# 再編集の往復：元の組版の記録と復元

2026-10-25。Issue #93。PR #92 マージ後の main `870709f` を起点とする。評価条件は、実装前の commit `dee0b04` で [manifest](../evaluations/paragraph_frame_roundtrip/manifest.json) に固定した（`355a923` で1点を追補、3.3）。結果は [results.json](../evaluations/paragraph_frame_roundtrip/results.json)。

## 結論

- 段落を最初に承認して保存するとき、その段落の描かれていた組版（文字ごとの位置・字送り・グリフ・文字コード、行、下の段落）を、PR #88 の承認済み条件の記録としてPDFのページに保存する。2回目以降の編集では、記録と同じ文字列に戻った行を記録した位置に置き、戻ってきた文字を記録した文字コード・字送りで描く。外部のファイルは使わず、保存したPDF単体から再編集できる。保存前の検査は緩めていない。
- 固定評価（PR #92 の15段落と後続段落が動く3段落、48系列・174手）で、元に戻した手（84手）の段落の変わらない文字が元の原点に戻った割合は 81.0% → **100%**（10,098/10,098）、改行 164/176 → **176/176**、ページの抽出文字列が MuPDF・Poppler とも元と同じ 58/80 → **84/84**、検索の件数 76/80 → **84/84**。ページの全グリフが一致しない12手は、すべて 0.001 pt 未満のずれ。
- 同じ編集を元に戻してもう一度行うと、1回目と同じに描かれる（段落の文字 4,602/4,988 → **5,016/5,016**）。繰り返しても組版は崩れない。
- PR #92 の固定評価の往復は 915 → **1,076/1,076**（C05 233 → 353）。他の指標は PR #92 と同じ。
- 保存 162 → 168、拒否 8 → 6。安全性（12手）と意味構造の不合格は従来と同じ手。品質の不合格は 4 → 6 手で、増えた2手は新たに保存できるようになった C04 の手（監査の期待値の作り方のため。保存したPDFは元のPDFと一致する、4.1）。PR #87〜#91 の回帰では、PR #90 の標本1件が丸めの境目のため品質不合格になった（5章）。どちらも基準は変えず、不合格として記録した。

## 1. PR #92 の往復で失われていたもの

PR #92 の固定評価の「再編集の往復」（編集して保存し、保存したPDFだけから元の文章に戻す）では、元の位置に戻った文字が 915/1,076 だった。失われた161文字は3段落に集中していた。

| 段落 | 編集 | 戻った文字 | 最大のずれ | ずれ方 |
|---|---|---|---|---|
| C05（Antenna House、欧文の両端揃え） | 折返しを伴う長文化を戻す | 233/353 | 0.14 pt | 改行位置は元に戻るが、1・3行目の空白が元より広く、行末が0.08〜0.14 pt 右に出る |
| C12（Distiller、1行のセル） | 短文化を戻す | 18/52 | 0.42 pt | 戻した語の文字が1文字ごとに 0.028 pt ずつ広く置かれ、後ろの文字がずれていく |
| C01（InDesign、和文） | 長文化を戻す | 105/112 | 0.12 pt | 戻した1文字の字送りが元と違う |

原因は共通していた。**保存したPDFは、編集前の組版を覚えていない。**

- 一度消えて戻ってきた文字は、元の描画での字送り（カーニング、字間の調整、`TJ` の数値）が分からないため、フォントの公称の字幅（欧文）や行の字送りの中央値（和文）で置かれる（C12、C01）。
- 両端揃えの行は、編集後のPDFに描かれている行末（編集で組み直された行末）に揃え直される。元の行末は行ごとに0.1 pt ほど違っていたが、その値は残っていない（C05）。
- 後続段落の扱いにも同じ原因の非対称があった（PR #92 の報告書の障壁7）。長文化で段落が下に伸びると、それまで後続でなかった段落が後続の距離に入り、元に戻す編集で上に引き上げられ、承認した編集枠の外の画素が変わるとして拒否された。

## 2. 方式：元の組版の記録

### 2.1 記録するもの

段落を最初に承認して保存するとき、その段落の描かれていた組版を、PR #88 の承認済み条件の記録（ページの `/PieceInfo`、`auto_conditions`）に加えて保存する（`prototypes/paragraph_frame/auto_restore.py`）。外部のファイルは使わない。

- `text`：段落の論理的な文字列（行の境目の暗黙の空白を含む）
- `glyphs`：文字ごとに、描かれていたグリフの `[文字, x, y, 字送り, グリフID, フォントリソース名, 文字コード]`。字送りは同じ行の次のグリフまでのペンの移動量（行末は null）。暗黙の空白は null
- `rows`：行ごとに `[開始, 終了, ベースライン, 行頭のx]`（文字の範囲）
- `below`：段落の下にある文字のかたまりの最初のベースラインと、それが後続段落だったか

2回目以降の承認では、記録をそのまま引き継ぐ（最初の承認の組版が残る）。後続段落として平行移動された段落の記録は、一緒に移動する。記録が不正な形のとき（他の製品の書き換えなど）は使わず、その時点の描画を新しい記録にする。条件の記録そのものが使えないとき（段落の描画が記録と一致しない、保護された描画が入ったなど）は、PR #88 と同じく記録全体を使わない。

### 2.2 使い方

記録を配置に使うのは、保存された記録が適用されたとき（2回目以降の編集）だけ。最初の編集では、記録は保存するだけで、配置は PR #92 と同じ。

- **文字の符号**：消えて戻ってきた文字は、記録した文字コードで、同じフォントリソースから描く（そのリソースがそのコードを同じ文字に読む場合）。1つのフォントに同じ文字のグリフが複数あることがあり（InDesign の府政だよりでは「抱」が CID 3658 と 622）、ページの別の場所の同じ文字（最初に見つかった方）では元のグリフにならない。

局所配置（`auto_local`）で、新しい文字列を記録の文字列と対応づける（difflib）。対応するのは、同じ文字で、同じフォントプログラムの同じグリフID（元のリソース、または元の符号がページから消えたあとの同じプログラムの新しい符号）の文字だけ。代替フォントの文字は対応させない。

- **行の復元**：行の始まりで、記録した1行の文字がそのまま続き、その後ろも記録と同じ文字が続く（または段落の終わり）なら、その行を記録した位置に置く。ベースラインは、記録の行と同じ行番号なら記録のベースライン（段落の1行目のずれを足す）、違えば現在の行送り。記録で行末の暗黙の空白にグリフがなかった行は、その空白を描かない（段落の文字列と ActualText には残る）。
- **字送り**：消えて戻ってきた文字は、記録の文字が後ろに続く範囲で、記録した字送りを使う。使うのは、記録の文字列がそのまま続き、まだ描かれている元の文字に届く範囲だけ（新しい語の中で記録の文字列と偶然一致した部分には使わない）。語間の空白には使わない（両端揃えの行では、記録した空白の幅は行の揃えで伸ばされた幅で、空白そのものの幅ではない）。
- **後続段落**：段落が短くなるとき、記録の時点で後続でなかった下の段落は、記録の位置より上には引き上げない（段落が伸びて後続の距離に入っただけの段落）。記録の時点で後続だった段落は、PR #88 のとおり段落との間隔を保って動く。

記録した位置は、配置の候補にすぎない。保存前の検査（保護された文字・描画との衝突、編集枠、両レンダラーの枠外の画素、抽出、意味構造）は、記録から置いた文字にも同じく適用する。

### 2.3 描き直す文字の字間・語間

描き直す文字は、元の描画の字間（`Tc`）と語間（`Tw`）のまま書く（ペンの位置の計算に含める）。描かれる位置は同じだが、保存したPDFを次に編集するとき、描き直した文字も元と同じ状態として読まれる。PR #92 までは `0 Tc 0 Tw` で書き、字間をグリフの位置に含めていたため、次の編集で新しい文字の字幅の計算（字間を足す）と、行の字送りの中央値が変わっていた（InDesign の府政だよりは `Tc` が約 −0.38）。同じ編集を元に戻してもう一度行うと、1回目と 0.4 pt ずれた。

### 2.4 局所配置の他の部分

変えていない。復元できない行（記録と文字が違う行）は、PR #92 の規則で配置する。

## 3. 固定した評価

### 3.1 対象と手順

実装前の main `870709f` で固定した（`roundtrip_evaluate --phase freeze`、`dee0b04`）。

- **対象**：PR #92 の固定評価の15段落（InDesign、Word、LibreOffice、Antenna House、LiveCycle、Distiller、TeX の Form XObject、canvas）と、PR #88 の連続編集のうち後続段落が動く3段落（Q1：LibreOffice の和文、Q2：Word P/Span、Q3：Word の直接の P）。
- **往復**：PR #92 の編集（同字数・短文化・長文化・折返しを伴う長文化）ごとに、編集 E → 元に戻す U → E → U の4手。各手は、前の手が保存したPDFだけから提案して保存する。48系列。
- **経路**：段落の離れた2か所の編集 A・B について、A → B → A を戻す、の3手の結果を、B だけを元のPDFに適用した結果と比べる。12系列。

### 3.2 指標

各手：保存、安全性・品質（`indesign_evaluate.audit`、前の手のPDFに対して、PR #90 から変更なし）、意味構造（`tagged_evaluate.structure_audit`）、保存したPDFだけからの再編集。

元に戻した手（U）は、元のPDFと比べる（PyMuPDF と Poppler だけで測る。エンジンには依存しない）：

- 段落の無変更の文字が元の原点（0.01 pt 以内）にあるか、フォントとサイズ、行数、改行
- 段落の外のすべての文字（後続段落、他の文字）が元と同じか
- ページのすべての文字（文字・原点・フォント・サイズ）が元と同じか
- ページ全体の抽出文字列が元と同じか（MuPDF・Poppler、そのままと空白を除いて）
- 戻した文字列の検索の件数

2回目の E は1回目の E と比べ、経路の結果は B だけの結果と比べる（同じ指標）。

### 3.3 追補

Q1〜Q3 は、PR #88 の連続編集と同じく、承認した代替フォント（PR #88 の manifest の `font`）を使う。最初に固定した manifest にはこれが抜けていて、Q1・Q2 の最初の手が「元のフォントにない文字」として拒否された。新しいコードで評価を実行する前に manifest に追補し（`amendments`）、従来B2の Q1〜Q3 も追補した条件で実行し直した。

## 5. 既存機能への影響

## 6. 評価の途中で見つけて直したこと

- **同じフォントプログラムの新しい符号を対応づけていなかった（Q3）。** Word の直接の P で、元の符号がページから消えたあと、戻ってきた文字は同じフォントプログラムの新しい符号（`source:` の font_key）で描かれる。記録との対応づけが font_key のある文字をすべて除いていたため、行が復元されなかった。同じプログラムの同じグリフIDなら対応づける（代替フォントは引き続き除く）。
- **同じ文字の別のグリフ（C01）。** InDesign の府政だよりで、同字数の編集を元に戻しても1文字が元に戻らなかった。「抱」のグリフがフォントに2つあり（CID 3658 と 622）、戻ってきた文字はページの別の場所の「抱」（別のグリフ）を手本に描かれていた。記録した文字コードで描く（2.2）。
- **字間（`Tc`）を書き直していた（C01）。** 同じ編集を元に戻してもう一度行うと、1回目と 0.4 pt ずれた。描き直した文字を `0 Tc` で書いていたため（2.3）。元の `Tc`・`Tw` のまま書く。
- **最初の編集にも記録を使っていた（C08）。** 実装の途中では、最初の編集でも、その時点の描画から作った記録を配置に使っていた。LibreOffice の C08 の同字数の編集で、変えていない文字が元の位置に残る数が PR #92 の 188 から 172 に減った。記録を配置に使うのは、保存された記録が適用されたときだけにした（2.2）。
- **偶然の一致と語間に記録の字送りを使っていた（C08・C03 ほか）。** 最終の評価の1回目（`a18de4b`）で、同じ編集を元に戻してもう一度行った結果（2回目の E）が、1回目の E と違う段落が7つあった（C08 の同字数では、元の位置に残る文字が 188 → 172）。原因は2つ。(1) 新しい語の中の文字が、記録の文字列と偶然一致した部分（「array」の「ra」と記録の「range」の「ra」、和文の語順の入れ替え）で、記録の字送りを使っていた。(2) 戻ってきた語間の空白に、記録の字送り（両端揃えで伸ばされた幅）を使い、そのうえで行を揃え直していた（C05・C08 の折返しを伴う長文化）。記録の字送りは、記録の文字列がそのまま続き、まだ描かれている元の文字に届く範囲だけで使い、語間の空白には使わない（行の揃えが決める）。この修正の後、全ケースを評価し直した（4章の数字は修正後の `2306a4e`）。
- **評価：Q1〜Q3 の代替フォント**（3.3）。
- **テストの期待値**：`tests/test_paragraph_frame_continuity.py` の短文化を元に戻すテストは、戻ってきた文字の手本の種類として `source-resource-witness` を期待していた。記録した文字コードで描くようになったため `recorded-source-code` に変えた（元のフォントから描き、代替フォントや新しい符号を使わない、という検査の意図は同じ）。

## 7. 残る課題

1. **最初の編集は元の組版を使わない。** 記録を配置に使うのは2回目以降の編集だけで、最初の編集は PR #92 の配置のまま（4.5）。実装の途中で最初の編集にも使ったときは C08 の結果が悪くなった（6章）。その原因の一部は、後で見つけた偶然の一致（6章）だった可能性があるが、最初の編集の配置を変えると PR #92 の固定評価の結果が変わるため、今回は変えていない。
2. **記録した行を使えるのは、行の文字列が記録と同じときだけ。** 同じ行に別の編集が残っている行は、PR #92 の規則で配置する（C06・C09 の経路、4.3）。行の中の変わらない部分だけ記録の位置に置き、変わった部分の前後で揃え直す方式が考えられるが、両端揃えの行で空白をどこで吸収するかの規則が要る。
3. **他の製品による保存。** 記録はページの `/PieceInfo` に置く。他の製品で保存し直すと、記録が消えるか、段落の描画が記録と一致しなくなり、PR #88 と同じく記録全体を使わない（PR #92 の配置に戻る）。外部のファイルに頼らない代わりの制約。
4. **記録の大きさ。** 文字ごとに7項目を持つため、C05（記録した文字列 425文字）で JSON が約 23.5 KB、Flate で圧縮して約 4.6 KB をページに加える。ページの段落を多く編集すると、段落ごとに加わる。
5. **監査の側の限界（基準は変えていない）。** PR #90 の安全性監査は、後続段落が動く編集（Q2・Q3）を、領域の外の変化として不合格にする。抽出の検査は、編集した出現位置を MuPDF のページの抽出順で数えるため、Form XObject のヘッダのように MuPDF が別の順序で読む文字列では、別の出現を期待値にする（C04、4.1）。
6. **PR #92 から残る障壁。** 長文化の拒否（後続段落の配置物、容量、保護された描画）、C10 の Poppler のページ全体の抽出順は、このPRの対象外で、変わっていない（PR #92 の報告書 8章）。PR #92 の障壁2（折返しを伴う編集の往復）と障壁7（後続段落の判定の非対称）は、このPRで解消した。

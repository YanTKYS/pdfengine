# 段落再構築（B2）の継続編集安定化と実PDF適用範囲

2026-10-22。PR #87 マージ後の main `279736f` を起点とする。評価条件は実装前の commit `8f93488` で [manifest](../evaluations/paragraph_frame_continuity/manifest.json) に固定し、以後変更していない（`continuity_preflight` で同一バイトを再生成できる）。結果は [results.json](../evaluations/paragraph_frame_continuity/results.json)。

## 結論

- **短文化で1行になった後も、承認した段落条件が保存PDFだけから復元されるようになった。** N2（タグなし）とタグ付き2原本の連続編集（短文化→元の文へ戻す→さらに長文化→別の置換）を各4回、毎回別プロセスでPDF単体から行った。3系列とも左端・右端・行送りが初回承認値のまま変わらず、**元の文へ戻すと元の行分割・x座標・baselineが完全一致した**。従来どおりの推定だけ（PR #87相当）では、3系列とも一致しなかった（N2：右端 566.9→487.5 pt、継続行の左端 28.5→34.1 pt、行送り 15.7→16.5 pt）。
- PR #87 の12要求は後退していない。初回の品質gate 8/12、PDF単体の再編集 11/12、無編集保存 12/12 で、件数も失敗した検査項目もPR #87と同じだった。元の書体programで描いたglyphは 953→978/1,022（93.2→95.7%）に増えた。
- 未使用の2原本（8要求）では、B2は3件を保存して品質gateまで合格した。英語3段組（両端揃え、行末の空白、画像の上の白文字）である。5件は公開前に拒否した。拒否理由は、合字の出所不明、容量不足（下の画像）、ソフトハイフンの移動、ToUnicodeなし（2件）である。A・B1は8件とも保存できなかった。
- 検索・コピーの品質未達16件は、**引き続き品質未達として管理する**。MuPDF・Popplerで期待どおりに検索・コピーできないことは、利用者にとって実際の不具合である。原因の切り分けとして、内部の描画文字列（描画順・ToUnicode）は16件とも要求と一致することを確認した。現象は、行をまたぐ検索（15件）と、読み取り時に推定で入る空白（1件、N4）である。Acrobatなど他の閲覧ソフトでは未確認である。検索に合わせるためのPDF改変はしていない。

## 1. 編集条件を保存後も使う方式の比較

| 方式 | PDF単体で再編集 | 一般PDFとの両立 | 外部変更の検出 | 判断 |
|---|---|---|---|---|
| 保存PDFからの再推定のみ（PR #87） | 可 | 可 | 不要 | 1行になると左端・行送り・右端の根拠が消える（N2で再現） |
| sidecar JSON | 不可（別ファイルが必要） | 可 | hashで可 | PDF単体の要件を満たさない |
| タグ付きPDFのLayout属性（`/A` の `/BBox`・`/StartIndent`・`/LineHeight` など） | 可 | **タグなしPDFでは使えない** | 不可（内容と結び付かない） | 意味構造を変える。他のソフトが値を検証せず書き換える可能性がある |
| XMPや文書単位のmetadata | 可 | 可 | 不可 | ページ・段落に結び付かない |
| **ページの `/PieceInfo`（PDF 32000-1 §14.5、製品固有のprivate data）** | 可 | 可（無い場合は従来の推定） | 記録した描画行と照合 | **採用** |

`/PieceInfo` の `/PdfEngineB2` に、JSONのstreamを1つ置く。中身は段落ごとのrecordである。

- **段落の同定**：保存時に実際に描いた行。行ごとの文字列、x、baseline、右端、font resource・サイズ・色。
- **承認した条件**：left・right・first_x・leading・bottom・alignment・frame。
- **由来（provenance）**：観測（例：1行目のx）、推定（例：占有幅の最大値、近傍行の左端、行間の中央値）、既定値（1.5 em）、保存済みの承認値、のどれかを値ごとに記録する。
- **origin**：最初に承認した値と、その由来。2回目以降の編集でも引き継ぐ。
- **承認回数**と、承認したproposalのSHA-256。

PDFは作者のframeを保存していないので、これは作者のframeの復元ではない。**利用者が承認した編集条件**として扱い、観測値・推定値と区別して提案画面に表示する。

**適用条件**：次の両方を満たす場合だけ、recordを適用する。

1. recordの全行が、文字列・位置・style（許容誤差0.01 pt）とも現在の描画と一致する。
2. 承認した幅の中に、保護対象（他の文字・図形・画像・注釈）が入り込んでいない。

それ以外は「stale」と表示し、新しく推定した値を使う。

- 外部ソフトがページの `/LastModified` を更新していても、描画と照合できればrecordを適用し、警告を出す。
- 内容が読めないrecord、または必須キー・値が不正なrecord（例：`records: [{}]`）は、警告を出して無視する。
- recordが無い一般のPDFは、PR #87と同じ推定で処理する。

段落が下へ平行移動した場合、その段落のrecordも同じ量だけ移す。

## 2. 実装（`prototypes/paragraph_frame/`）

- `auto_conditions.py`：recordの読み書き、照合、staleの判定。読み込み時に各recordの必須キー・型・数値範囲（ページ内、left < right、行送り > 0、揃え方、承認回数）を検証する。不正なrecordは警告を付けて破棄し、その段落は推定に戻る。正常なrecordの扱いは変えない。破棄したrecordは次の保存に持ち越さない。
- 保存時の処理（`auto_writer.store_conditions`）：
  - 書き出したPDFを、次のproposalと同じ解析器で読み、編集後の段落の行を記録する。
  - 他の文字から分離できない行は記録しない。
  - 公開前に、記録したrecordを読み戻せて現在の描画と一致することを検証する（`verify_conditions`）。
- `auto.propose(..., stored_conditions=False)` を指定すると、PR #87相当の推定だけで提案する（比較評価用）。
- 実PDFの評価で見つかった、PDFの種類に依存しない改善：
  - **削除済みの文字を元のfontで描き直す**（resource witness）。描画が消えた文字でも、元のresourceのToUnicodeの逆引きが一意で、CID/cmap→GIDのglyphに輪郭があり、`/W` が programの送り幅と一致すれば、元のcodeで描く。
    - LibreOfficeは1つの書体を256文字ずつの複数subsetに分けて埋め込む。同じ書体・同じdescriptorのsubset（sibling）も、元のcodeの出所として使う（`sibling-subset-witness`）。
  - **代替fontを書体の基準にしない**：前回の編集で代替fontで描いた字を、新しい字の書体の基準にしない。同じサイズで、最も近い元resourceの字を基準にする。
  - **和文の詰めを保持する**：Wordが行った約物の詰め（「、」10.56→6.71 pt）と、文字ごとの詰め（10.56→10.44 pt）を残す。詰めが行末の文字を押し出すときに限り、新しい字にも、元の段落で観測された量まで（最大0.05 em）同じ詰めを使う。
  - **段組みと段落の区切り**：同じbaselineを共有する段組みでも、行を正しくまとめる（横方向の重なりで列を判定）。行間がそれまでの行送りより明らかに広い場合や、次の行の最初の英単語が前の行に収まる場合は、段落の区切りと判定する。
  - **英文の改行と両端揃え**：英文の行末の改行を、空白として扱う（描画されない空白）。行末の空白は、行幅の判定に含めない。両端揃えの英文段落は、単語間の空白を均等に広げて組み直す。
  - **行末ハイフン**：行末のハイフンがソフトハイフンかどうかは判断できないので、行の途中へ移すような組み直しは拒否する。
  - **背景**：段落の全行を含む塗り・画像（ページ全体の白い塗り、段の背景画像）は、障害物ではなく容器として扱う。新しい文字はその内側に収める。
  - **拒否理由の明示**：合字（ffi等）を含む描画命令の文字は描画元を追跡できないので、そのことを理由として拒否する。従来は「描画順の不一致」と誤って表示していた。
  - **代替fontの候補選び**：利用者が承認した複数の代替font候補から、元の文字との「字の太さ（em内のインク密度）」の差が最も小さい候補を、元のfontごとに選ぶ（詳細は5章）。

## 8. 残る障壁と次の技術選択

1. **行をまたぐ検索・推定空白（品質未達）**：内部の文字情報は正しいが、MuPDF・Popplerでは検索・コピーの結果が期待と異なる。Acrobatなど他の閲覧ソフトでの確認と、行末の扱い（改行位置、空白・ActualTextの付け方）でPDF側から改善できるかの検討が残る。
2. **合字・ToUnicodeのないfont**：1つのglyphが複数の文字を表す場合、描画元を追跡するには、cluster単位の対応付けが必要になる。ToUnicodeがないfontの文字列で選択するには、OCRか利用者による文字の対応付けが必要で、今回の範囲外である。
3. **移動できない後続物**：画像や他の段の下端で容量が尽きる。段落を次の段・ページへ流す（continuation）か、利用者が明示的に枠を広げる仕組みが必要になる。
4. **ソフトハイフン**：ソフトかハードかを区別する情報がPDFにない。英文で組み直す範囲を広げるには、辞書を使ったハイフネーションか、利用者による確認が必要になる。
5. **代替fontの字面の大きさ**：太さの近さだけでなく、ascent・descentが行間に収まるかも候補選びの条件にするのが、次の改善になる。
6. **records の寿命**：別のソフトが段落を描き直すと、recordはstaleになり、推定に戻る（安全側）。条件を他のソフトと共有するには、タグ付きPDFならLayout属性にも書くのが選択肢である。ただし意味構造を変えるので、今回は採用していない。

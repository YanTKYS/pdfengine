## 1. 実用成功の判定（`eval_records.practical`）

### 1.1 必須の基準と出典（変更前に `before.json` の `criteria` に固定）

承認変更監査（`approved_audit`）を記録した手（スモーク・パネル）の判定。基準ごとに、出典・結果・役割を `practical_basis` に残す。

| 基準 | 出典 | 役割 |
|---|---|---|
| 保存 | 手の結果 | 必須（拒否は false、未実行・入力不足は null） |
| 承認・承認した変更・保護 | `approved_audit` の判定（承認の確認、承認した変更が承認どおり、承認範囲外の文字・描画・画像・注釈・画素・他ページ・フォントが不変） | 必須 |
| 品質 | `approved_audit.quality`（ページの抽出、大きさと色、下の2つ） | 必須 |
| 自然な配置（新設） | `approved_audit.quality.placement` | 必須 |
| 編集箇所の検索・抽出（新設、選択肢 b） | `search_copy.verified` | 必須（削除は対象外） |
| 意味構造・リンク | 構造監査・リンク監査 | 必須（PR #117 のレビューで「失敗してはならない」から変更。7章） |
| 旧監査（領域）の保護・品質、移動の監査 | `indesign_evaluate.audit`、`moves`・`placement`・`raster` | 忠実編集：失敗してはならない。承認したレイアウト変更：表示のみ（失敗のまま残す） |
| 変更前の品質（`legacy`） | 旧の `search_mupdf` で計算した品質 | 表示のみ |

- 必須の基準が1つでも false なら false。必須の基準が1つでも null なら null（未検証）。
- 承認したレイアウト変更の手とは、保存がその変更（配置物・行の装飾・連鎖の要素・パネルの伸長）を記録し、承認変更監査の変更集合にもある手。どちらか一方だけなら忠実編集として扱う。忠実編集では旧監査の失敗を数える。
- 承認変更監査のない手（連鎖・装飾など、864記録の大半）は、従来どおり旧監査で判定する。その検索の判定は編集箇所で測っていない（3章、判断事項 2）。

### 1.2 編集箇所の検索・抽出（`search_copy.verified`）

| 置換が描かれた行 | 必須の指標 | 記録するだけの指標 |
|---|---|---|
| 1行 | `search_full`（1回の検索で、描かれた場所に見つかる）、`extraction_mupdf`、`extraction_poppler`、`copy_equivalent` | — |
| 複数行 | `search_per_line`（各行の部分がその行で見つかる）、`extraction_mupdf`、`extraction_poppler`、`copy_equivalent` | `search_full`（置換全体を1回の検索で探せること。保証しない） |

- 必須の指標が1つでも false なら不合格、null なら未検証。
- 元のPDF由来の隙間（`as_in_source`）は合格の理由にしない。
- 実クリップボード（`clipboard_manual`）は null のまま。`copy_equivalent` は PDF の抽出によるコピー相当で、クリップボードの試験ではない。
- 複数行で合格した記録には「行ごとに検証済み。1回の検索で置換全体を探せることは保証しない」と注記する。

### 1.3 自然な配置（`approved_audit.quality.placement`、新設）

スモーク・パネル・連鎖の評価は、旧監査に段落の行を渡していなかった。そのため旧監査の配置の確認（基線が段落の格子上、左端）が、それらの手では測られていなかった。それでも実用成功に数えていた（3章）。編集した段落の行について、次を測る。

- 描かれた各行が提案の基線にあり（0.2 pt）、提案の各行が描かれている。
- 元の行の基線が保たれている。
- 追加の行が提案の行送りにある。
- 各行が段落の左端（1行目は1行目の開始位置）から始まり、右端の内側で終わる（0.3 pt）。
- 行送りの根拠（段落で観測、または保存時に推定として承認した既定値）を記録する。根拠の良し悪しはここで判定しない（判断事項 1）。

## 6. 判断事項

設計者の方向（PR #117 のレビュー）。このPRでは、どれも現状のまま実装していない。

- 1：元由来というだけで救済しない現状を保つ。未編集部分が同一であることを厳密に証明して範囲を分ける案は、後続の Issue で検討する。
- 2：このPRでは再監査を求めない。全体を比べるときは「検索は未測定」と明示する。
- 3：提案が既定値と根拠を示し、編集操作ごとに `acknowledge_inference` で承認された範囲に限り、提案位置との一致による「自然な配置」の判定を採る。利用者が画面で見た目の自然さを確かめた証拠ではない。
- 4・5：後続の独立した Issue で扱う。

1. **段落の抽出を、編集箇所の外の元の隙間も含めて求めるか**（製品契約）
   - 現在（Issue の選択肢 b のとおり）：段落全体の両抽出が一致することを求める。
   - そのため、LibreOffice の文書では編集と関係のない場所の隙間（元の文書にもある）でも不合格になる。スモークの L1・L3 は成功から不合格になった。
   - 代替案：
     - (a) 現在のまま。
     - (b) 抽出を、置換とその前後の字までに限る。それ以外の違いは、元の文書と対応する（同じ字形の間の同じ空白：`as_in_source`）ときだけ、編集によるものではないと扱う。
       - L3（隙間は編集箇所から遠い）は合格になる見込み。
       - L1（隙間が置換の先頭の字の隣）・S-L2・L8（隙間が置換の中）は不合格のまま。
       - `as_in_source` による救済になるので、設計判断が必要。
2. **承認変更監査のない評価（838記録）の検索の判定**
   - これらは旧監査の `search_mupdf`（ページのどこかで見つかれば合格）で実用成功を決めている。このPRでは変えていない。
   - 代替案：
     - (a) 節目の評価で、各評価の保存結果に承認変更監査（`approved_audit.compare_runs`）をかけ、編集箇所の検索・抽出を測る。
     - (b) 旧監査の `search_mupdf` を、編集した行で測るように直す（測定誤りの修正。多くの記録の実用成功が変わりうる）。
3. **観測していない既定の行送りで足した行を、自然な配置とみなすか**
   - L2・L6・L8・I4・A1 は、1行の段落を2行にする。追加の行は、元の文書で観測できない既定の行送り（1.5 em）で置く。保存時に推定として承認している（`acknowledge_inference`）。
   - 今回は、提案どおりに置かれていれば配置の確認を合格とし、根拠（`leading_basis`）を記録した。A1・I4 は以前から実用成功に数えていた。
   - 代替案：観測していない行送りの行を「未検証」とする。その場合、L2・L6・A1・I4 の実用成功は未検証になる。

# B2の段間再組版（Column Flow）：同一ページの横段への継続

2026-10-22。PR #88 マージ後の main `6b4d4f9` を起点とする。評価条件（原本、編集対象、期待結果、移動してよい範囲）は、実装を評価する前の commit `67048df` で [manifest](../evaluations/paragraph_frame_column_flow/manifest.json) に固定した（第1版）。PR #89のレビューを受けて継続の確定条件を厳しくしたため、新しい規則を評価する前の commit `4f9aaf7` で第2版に改訂した（§9）。結果は [results.json](../evaluations/paragraph_frame_column_flow/results.json)。

## 結論

- **段落を長くして今の段に入りきらないとき、論理的につながる次の段へ文章を流せるようになった。** 短くしたときは、次の段の文章を前の段へ引き戻す。編集した段落だけを改行し直し、後続の行は字形・改行位置・段内の位置を保ったまま段の間を行単位で移動する。白抜き・再描画、文字の縮小、領域の拡大はしない。
- **これは生成PDFでの成功であり、実PDF一般での成功ではない。** 到達できた実PDFには、同じページの中で段から段へ本文が続く例がなかった（§6）。そのため、段間で文章を流せることはLibreOfficeで生成したPDF（本当にスレッドでつながった2段組）で確認した。実PDFでは「段内に収まる編集が従来どおり動くこと」と「無関係な隣の段を選ばないこと」を確認した。
- **継続を自動で確定するのは、1つのタグ付き段落（`/P`）が段の切れ目をまたぐと構造で確認できる場合だけである**（レビューによる修正）。タグなしPDFで段落の途中で段が切れている場合や、連続する `/P` は「候補」とし、利用者がidで承認したときだけ使う。前の段が文の途中で終わっていても、続きは別のページにあり、隣の段は同じ書体の別記事かもしれないからである。承認はPDFに保存するので、再編集のたびに承認する必要はない。
- 固定した29手順（第2版）は、29件とも期待どおりの結果になった。内訳は保存20件、公開前の拒否9件である。保存した20件は、次の4つの観点に分けて評価し、すべて合格した。
  - **保存成功**：20/20
  - **安全性合格**：20/20
  - **品質合格**：20/20（MuPDF・Popplerでの抽出と検索、禁則、行送り、左端・右端、書体の不変）
  - **継続編集合格**：20/20（保存したPDFだけから次の提案を作ったとき、保存済みの承認条件が使われる）
  - このうち実PDFは1件（enterpriseの段内編集）だけである。
- **段の継続の認識**は、manifestで固定した14組（生成10、実PDF 4）で14/14が正しかった。同じ書体・見出しなし・行もそろった別記事の段（新しい負例）は、タグなしでは候補（承認しなければ使わない）、タグ付きでは却下になった。実PDF 7ファイル・31ページで調べた109個の「段→右隣の段」候補は、すべて根拠付きで却下した。誤って継続と判定したものは0件である。ただし実PDFには本当の継続がないので、実PDFでの見逃し率は測れていない。
- 既存のB2は後退していない。PR #87の12要求、PR #88の連続編集3系列×2方式、未使用原本8要求は、いずれも結果・失敗項目・行分割がPR #88と同じだった。

## 1. 既存コードとPR #86〜#88の確認

- B2は、選択した段落を推定した1つの枠（frame）の中で改行し直す。後続段落は、同じ段の中で縦に平行移動するだけである。段の下端は「次の保護対象（画像・他の文字など）またはページの端」なので、段組では次のことが起きていた（main `6b4d4f9` で再現）。
  - **長くしたとき**：1段目がページ下の余白まで伸び、2段目と下端がそろわなくなる。2段目に続く文章は2段目に残ったままである。
  - **短くしたとき**：1段目の最終行が空き、2段目の先頭行は2段目に残る。
- PR #88のE3（enterprise p2、1段目の段落を長くする）が拒否されたのは、後続段落の下に画像があるためだった。今回あらためて確認すると、2段目は別の記事である（画像の上の白文字、見出し「Impress」から始まる）。E3には同じページで続く段がない。今回もE3は拒否のままで、2段目へは流さない（§5）。
- 実装は、新しい描画engineではなく、B2の部品（段落の認定 `qualify`、書体のtoken化 `build`、行に入る位置の判定 `fit`、書き込みと公開前検査 `write`/`validate_stage`、`/PieceInfo` の条件）を共通に使う。段組の論理的な流れ（flow）を表す層を1つ足し、段の継続が証明された場合か、利用者が候補を承認した場合だけ新しい経路を選ぶ。

## 2. 段の論理的な流れの推定（`auto_flow.py`）

### 2.1 段（column block）

同じ大きさの段落を、縦に積み重なり横方向に重なるものごとにまとめる。段ごとに次の値を観測する。

- **左端**：2行目以降のx
- **右端**：インクの最大の右端
- **上端・下端**：最初と最後の行のbaseline
- **行送り**：段落内の行間隔のうち、最小値に近いものの中央値
- **段落間隔**：段落と段落の間のbaseline間隔の中央値
- **本文の書体**：最も多いfont resource・サイズ・色

行の解析で横に並ぶ2つの段の行が1行にまとめられることがあるため、ガターで行を分ける（`split_gutters`）。分けるのは次のどちらかの場合である。

- インクの間隔が1.8 emを超える。
- インクの間隔が0.9 emを超え、かつ右の字が左の字の直後に描かれていない（描画順が飛んでいる）。

### 2.2 段Aから右隣の段Bへのつながり（link）

次の条件のどれか1つでも満たさなければ **却下（rejected）** する。却下の理由は、満たさない条件をすべて記録する。

1. 本文の書体・サイズ・色が同じで、Bの先頭が同じ本文の書体である（見出しで始まらない）。
2. 行送りが同じ（差が5%以内）。
3. 段の幅が同じ（差が0.5 em以内）。後続行を、改行し直さずにそのまま移せる条件である。
4. 2つの段が同じ最初の行から始まる（上端の差が行送りの半分以内）。
5. AがB以上に深い位置まで埋まっている。
6. Bの列で、Bの本文より上に保護された描画（画像・図形・注釈）がない。
7. Aの最後の字とBの最初の字の間に、他の文字が描かれていない（描画順）。

条件をすべて満たしたものを、根拠の強さで分ける。

| 区分 | 根拠 | 扱い |
|---|---|---|
| 確定（determined） | タグ付き：1つの `/P` が段の切れ目をまたぐ（同じ段落が2段にあることを構造が示す） | 自動で使う |
| 候補（candidate） | タグなし：Aの最終行が段の右端まで埋まり、文末記号で終わらない（段落の途中で切れて見える） | **利用者がidで明示的に承認したときだけ**使う。承認すると2つの部分を1つの段落として組み直す |
| 候補（candidate） | タグ付き：同じ親の下で連続する `/P`（読み順は連続するが、同じ文章の流れとは限らない） | 同上 |
| 候補（candidate） | タグなし：条件はすべて満たすが、切れ目が段落の境界にある | 同上 |
| 却下（rejected） | 上の条件を満たさない、またはタグ付きPDFで構造がつながらない | 使わない。理由を提案と拒否メッセージに表示する |

文の途中で切れていることと、隣の段がその続きであることは同じではない。前の段の記事が別のページへ続き、隣の段に同じ書体の別記事が並ぶ場合、書体・行送り・幅・描画順はすべて一致する（§5の `gen_columns_ja_articles`）。そのため、幾何と描画順だけでは確定しない。

候補のidは `column a->b`（段の番号はページ内の検出順）である。`recognize()` またはCLIの `columns` で一覧を出し、`propose(..., continuation=['column 1->2'])` で承認する。

### 2.3 タグ付きPDF

LibreOfficeの出力に合わせて、段落の認定を一般化した。

- RoleMapでたどった標準の型を使う（`/Standard` → `/P`）。
- `/A`（Layout属性）は、変えずに残す。
- 1つの `/Span` が行ごとの複数のMCIDを持つ構造を受け付ける。
- `/Artifact` の領域は意味構造の検査から除く。

PR #88までのWord形式（`/P` の下に `/Span` が1つずつ）も、引き続き扱える。

## 3. 段をまたぐ組み直し

- **領域（region）**：流れに属する段ごとに1つ作る。
  - 左端・右端・上端は、観測したそれぞれの段の値である。
  - 下端は、流れの中で最も深い元の行のbaselineで、すべての段に共通である。
  - 段の下に保護された描画があれば、そこで下端を止める。
  - 領域は広げない。入らない分は「容量不足」として拒否する。
- **編集した段落**は、領域を順にたどって改行し直す。
  - 改行位置はUAX #14で決め、行の後半が4文字未満になる場合は直す。両端揃えも従来のB2と同じ規則である。
  - 段の切れ目で分かれていた段落は、1つの論理段落として扱う。
- **後続の行**は、改行し直さない。字形・改行位置・段内のx方向の位置を保ち、行送りと段落間隔に従って次の位置へ順に移す。段の先頭の行には段落間隔を入れない。
  - 位置が変わらない段落は書き直さない。
  - 書き直せない段落（`qualify` を通らない）を動かす必要がある場合は、拒否する。
- 書き込みは、移動する段落の元の描画を取り除き、元の書体のコードと、元のマーク付き内容（MCID）のまま描き直す。
  - 描画順は読み順（段落順）と同じである。
  - 構造ツリーとParentTreeは変えない。
- 公開前の検査（`validate_stage`）は、領域ごとの枠に一般化した。追加した字が、どれかの領域の枠に収まるかを調べる。

## 4. `/PieceInfo` の条件との統合

- 保存時に、流れ全体を1つのrecord（`kind: "flow"`）として `/PdfEngineB2` に保存する。中身は次のとおりである。
  - 流れのすべての描画行と、各行が属する段落の番号
  - 承認した領域、行送り、段落間隔、揃え方
  - つながりの根拠（承認した候補を含む）
  - 由来（provenance）と承認回数
- 次の編集では、記録した行がすべて同じに描かれていれば、そのrecordを適用する。段落の区切りと領域はrecordから取る。
  - そのため、短くして2段目の段落がすべて1段目へ戻った後や、候補を承認した後も、PDF単体から同じ流れで再編集できる。承認した候補は、承認済みとしてrecordに残るので、再編集のたびに承認する必要はない（S1・S3の手順2以降、S5手順3、テスト `test_shortening_pulls_the_next_column_back`）。
- 次の場合はstaleとして扱い、推定に戻る。理由は警告に表示する。
  - 外部の変更で行が変わった。
  - 承認した領域に、他の描画や文字が入った。
- 流れの中にある単一段落のrecordは、流れのrecordに置き換える。recordの検証（`valid_flow`）は、行・段落番号の順序・領域・間隔・揃え方・承認回数を確認する。

- 確定・候補は0件で、109組すべてを却下した。
- 却下の主な理由は、書体・色の違い、段の上端の不一致、間に描かれた他の文字・見出しの帯である。
- 本当の継続が実PDFにないので、ここで分かるのは「誤って継続と判定しない」ことだけである。見逃しの割合は、生成PDFでしか確かめていない。生成PDFでは、本当の継続6例をすべて確定か候補にした。
- タグなしPDFでは、本当の継続（gen_columns_ja）と別記事（gen_columns_ja_articles）を、描画だけでは区別できない。どちらも候補になる。この区別は、利用者の承認に委ねる。

## 6. 編集可能な範囲はどれだけ広がったか

| 例 | 既存B2（main） | 今回 |
|---|---|---|
| gen_columns_ja、2段落目を長くする | 1段目が下の余白へ伸びて保存される（段の下端がそろわない）。2段目へは流れない | 候補を承認すれば、段の範囲の中で**322文字（約15行）まで**追加できる。超えると拒否。承認しなければ拒否 |
| gen_columns_en、3段落目を長くする | 同上 | 候補を承認すれば**900文字まで**追加できる |
| タグ付きで1つの `/P` が段をまたぐ場合 | 同上 | 承認なしで、同じ範囲まで追加できる |
| 短くする | 1段目の下に空行が残り、2段目の先頭行はそのまま | 2段目の行を1段目へ引き戻す |
| 段落の境界で切れる段組（タグなし、タグ付き） | 下の余白へ伸びる | 承認がなければ拒否する。承認すれば流す |
| 同じ書体の別記事が隣に並ぶ段 | 下の余白へ伸びる | 承認がなければ拒否する（タグ付きで構造がつながらなければ却下） |
| 見出し・図形で始まる隣の段 | 下の余白へ伸びる | 拒否（段の下端を超えない） |
| 実PDF（enterprise・府政だより） | E1・E4・E5は保存、E2・E3・E6は拒否 | 同じ（段組の流れが使える実例はない） |

実PDFで編集できる件数は増えていない。段組の流れで保存できたのは生成PDFだけである。

## 7. 既存のB2との違い

| | 既存のB2 | 段組の流れ（今回） |
|---|---|---|
| 容量 | 推定した1つの枠。下端は次の保護対象かページの端 | 流れの段ごとの領域。下端は元の最も深い行で、広げない |
| 後続の段落 | 同じ段の中で縦に平行移動 | 行単位で段の間を移動する（改行位置は保つ） |
| 段落の範囲 | 1つの段の中 | 段の切れ目をまたぐ論理段落 |
| 根拠 | 段落と枠の推定 | 段のつながりの根拠（確定／候補の承認／却下の理由） |
| 保存する条件 | 段落ごとのrecord | 流れ全体のrecord（全行、段落の番号、領域） |
| 横に並ぶ同じ書体の段がある場合 | 下の余白まで伸びる | 流れに属さない段落は、横の段と共通の下端を超えられない |

最後の行の規則は、既存B2の容量を狭める唯一の点である。書体・サイズ・色が異なる段は独立した枠として扱い、従来の容量のままにした（E5：画像の上の白文字は、PR #88と同じく保存）。

既存B2が受け付けるPDFを広げた変更が2つある。ガターでの行の分割と、LibreOffice形式のタグ（RoleMap・`/A`・複数のMCIDを持つ `/Span`）である。いずれもPR #87・#88の回帰結果を変えていない。

## 8. 残る拒否理由と次の課題

1. **容量不足**：流れの領域が満杯の場合。ページ・段を追加して流すことは範囲外である。
2. **候補の未承認**：タグなしPDFのすべての継続、タグ付きPDFで段の切れ目が段落の境界にある継続。
3. **段の不一致**：書体・色・幅・行送り・上端が違う、見出しや図形で始まる、間に他の文字がある。
4. **編集できない文字**：拡大した文字座標（InDesignの `Tm 9.6 0 0 9.6`）とForm XObject内の文字（府政だより）、合字・ToUnicodeなし、ソフトハイフン（PR #88から継続）。府政だよりを編集するには、文字座標の拡大を扱う変換と、Form XObjectの書き換えが必要である。
5. **段の幅が違う流れ**：後続行をそのまま移せないので、拒否する。必要なら後続段落も改行し直す方式に切り替える。
6. **段落の分離制御（widow/orphan）**：段の切れ目で1行だけ残る場合も、そのまま流す。元の文書の設定はPDFにない。

## 9. 注意事項

- **生成PDFの文字の欠落**：LibreOffice 24.2は、両端揃えの日本語の行末にある約物を2か所描画しなかった（「ため、」の読点、「ください。」の句点）。これはPDFに描かれていないので、評価では描かれた文字列（固定した描画行）を正とした。段落を組み直すと、行末で見えなかった欠落が行の途中に見えるようになる。
- **manifestの改訂（第2版、commit `4f9aaf7`）**：PR #89のレビューで、タグなしの「段落の途中で切れている」ことと、連続する `/P` だけで継続を確定するのは弱いと指摘された。前の段の記事が別のページへ続き、隣に同じ書体の別記事が並ぶ場合があるからである。第2版の変更点は次のとおり。
  - 確定は、1つのタグ付き `/P` が段をまたぐ場合だけにした。
  - S1・S3の手順1とJ-capacityは、候補を承認する入力にした。
  - S6は、承認なし（拒否）と承認ありの2手順にした。
  - 認識の期待値を新しい規則に合わせた。
  - 負例として `gen_columns_ja_articles`（タグなし・タグ付き）を追加した。
  - 原本・編集文字列・期待する文章は変えていない。第1版の原本の記録もそのまま残した。
  - 第1版での結果（26手順すべて期待どおり、ただしタグなしの継続を自動で確定）は、commit `8ea34d2` の results.json にある。
- **候補idの対応付け**：manifestでは、候補を本文の段の順番で `column 0->1` と書いた。実装のidは、タイトルも含めて段を数えるので `column 1->2` になる。評価では、manifestの段のx範囲と一致する候補を、提案に表示されたidで承認した。
- 府政だよりはscratchに置いた原本を使い、URLとSHA-256をmanifestに記録した。コミットしていない。
- Acrobatなど他の閲覧ソフト、Windows、人による操作での確認はしていない。

## 10. API・CLI

```python
from prototypes.paragraph_frame.auto import propose, approve, save
from prototypes.paragraph_frame.auto_detect import recognize

recognize('in.pdf', 1)                       # 段、つながり（確定・候補・却下と理由）、流れ
p = propose('in.pdf', 1, old, new)           # 確定した流れは自動で使う
p = propose('in.pdf', 1, old, new, continuation=['column 1->2'])   # 候補を明示的に承認
save('in.pdf', approve('in.pdf', p, acknowledge_inference=True), 'out.pdf')
```

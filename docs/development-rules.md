# 開発判断ルール

Issue #107 の設計側の回答（[1.1](https://github.com/YanTKYS/pdfengine/issues/107#issuecomment-6489059193)、[1.2〜6](https://github.com/YanTKYS/pdfengine/issues/107#issuecomment-6489151111)）を、開発の標準ルールとしてまとめる。要点は `CLAUDE.md` にも置く。テストの実行方針（focused tests 優先、full suite は任意）は `CLAUDE.md` のとおりで、ここでは変えない。

## 1. 最終目的と編集の方式

- 最終目的は、**既存の日本語PDFの文章を実用的に編集できること**。対象は自治体広報誌に限らない。同じ文字数の置換、短文化、長文化、部分編集、保存後の再編集をすべて重要な利用場面として扱う。
- **既定は忠実編集**。元の位置・書式・描画を保てるならそれを優先し、既存の保護と監査を保つ。
- 文章変更に必要な**レイアウト変更**（背景パネルの伸長、行間調整、後続要素の再配置など）は、**編集操作ごとの明示承認**で許容する。
  - 文字サイズの変更は、ほかと区別して示し、承認を得る。
  - 変更の種類ごとの数値（変更量の上限など）は後続の Issue で決める。それまで実装側で独自に決めない。
  - 承認は包括承認ではない。各編集で、変更前後・移動や変形する範囲と内容・影響しない保護領域を示す。承認がないとき、条件を証明できないときは安全に拒否する。
- 禁止：文字の画像化、白塗りによる見かけだけの置換、無関係な内容の破壊・隠蔽。
- 利用者に見せる承認は、変更前後の視覚的な差分と説明を基本とする。演算子の範囲・SHA・MCID などは再検証のための内部証拠として残すが、利用者に理解を求めない。評価器がすべての候補を承認することは、実際の UI の根拠にしない。

## 2. 成功の階層

各ケースを次の項目に分けて記録し、混同しない。忠実編集とレイアウト調整（承認した移動・伸縮を伴う編集）は分けて集計する。

| 項目 | 意味 |
|---|---|
| ① 保存成功 | 編集要求を承認して保存したPDFが開け、依頼した文字変更が反映された。実用成功を意味しない |
| ② 実用成功（最重要） | ①に加え、意図した文字列の検索・コピー／抽出、読める自然な配置、承認範囲外の文字・描画・画像・注釈・リンク・意味構造の保護、重なり・はみ出しがない、必要な承認が満たされる |
| ③ 再編集成功 | 保存したPDFだけを開き直し、別の文字編集を安全に続けられる |
| ④ 復元成功 | 開き直した後、元の文章へ戻し、元の位置・描画・意味・リンクに戻せる。②の必須要件ではない独立の指標。可否と理由を隠さない |
| ⑤ 拒否 | 危険な編集を拒否したことは安全性の結果として別に集計する（成功を装った失敗にしない）。期待が拒否のケースでは、拒否の妥当性を確かめる |

- 画素の完全一致だけを品質の唯一の指標にしない。意図した差分、文字の意味と抽出、配置の自然さ、承認外の保護を見る。
- **未検証は合格と扱わない。** 測っていない項目は「未検証」と書く。入力PDFがなければ「入力不足」と書き、成功にも失敗にも数えない。

## 3. 判断の委任

| 区分 | 内容 |
|---|---|
| **実装側で判断してよい** | 既存の安全・製品契約を満たす範囲の実装方式、局所的なリファクタリング、明白なバグ修正、テストの追加、評価器の測定不具合の修正（修正前の結果・理由・影響を残し、比較できることを説明する） |
| **設計側の判断が必要** | 元の仕様・成功基準の変更、安全な拒否条件の緩和、許すレイアウト変更の種類と量、既存テストの**契約**の変更、固定した評価の合否・期待の実質的な変更、広い範囲に及ぶ振る舞いの変更、別の編集対象に及ぶ承認の一般化 |

- 判断が分かれるときは、既存の安全な振る舞いを保つ。判断待ちの内容は組み込まず、代替案と影響を PR の「判断事項」に書く。安全に確定できる範囲は先に進めてよい。
- 既存のテスト・評価器の期待を変えるときは、どちらかを明記する。
  - **測定誤りの修正**（テスト・評価器が間違っていた）：実装側で判断できる。修正前の結果を残し、比較する。
  - **製品契約の変更**（期待する製品の動作を変える）：設計判断が必要。
- 固定した評価の結果は書き換えない。基準を更新するときは、変更前・変更後・理由・増減・設計判断の要否を差分として記録する（[evaluations/baseline](../evaluations/baseline/README.md)）。

## 4. Issue と PR の標準の記載

Issue（`.github/ISSUE_TEMPLATE/development.md`）：

- 目的と背景
- 委任してよい事項と、設計判断が必要な事項
- 変更前に固定する評価（ケース・手順・合否基準）
- 完了条件

PR（`.github/pull_request_template.md`）は、次を簡潔に書く。

- 改善前後
- 実PDFと fixture の区別
- 安全性・品質（実用）・再編集・復元
- 実行したテストと未実行のテスト（件数・時間・範囲）
- 判断事項（なければ「なし」）。既存テスト・評価器の期待を変えた場合は、測定誤りの修正か製品契約の変更かを明記する

## 5. 評価の3段階

入口は `prototypes/paragraph_frame/eval_hub.py`。詳細は [evaluations/baseline/README.md](../evaluations/baseline/README.md)。

| 段階 | いつ | 内容 |
|---|---|---|
| **通常**（`--tier normal`） | すべての PR | 変更したモジュールの focused tests、実PDFの代表スモーク、直接影響する固定評価（対応表で選ぶ） |
| **関連**（`--tier related`） | 変更が機能群に及ぶとき | 変更が及ぶ機能群（段落推定・装飾・連鎖・保存後の編集など）の固定評価 |
| **節目**（`--tier milestone`） | 共通エンジンの重要な変更、リリース、利用者の依頼など | すべての固定評価（4〜6時間） |

- 通常の PR に、4〜6時間の全評価を求めない。
- 評価の結果は、共通の基準（`evaluations/baseline/baseline.json`）と比べる。過去の PR の記録を何段も比べることはしない。
- 評価の対象を選んだ理由（変更したファイルと対応表）と、実行しなかった評価を記録する。対応表に漏れが分かったら更新する。

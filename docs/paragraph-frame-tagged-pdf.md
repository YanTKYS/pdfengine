# タグ付きPDFの編集：意味構造を保つ段落編集

2026-10-23。PR #90 マージ後の main `2aefe3e` を起点とする。評価条件は、実装前の commit `8e51d21` で [manifest](../evaluations/paragraph_frame_tagged/manifest.json) に固定した。結果は [results.json](../evaluations/paragraph_frame_tagged/results.json)。

## 結論

意味構造が原因で編集できなかった段落の多くを、構造を変えずに編集できるようにした。

- **135段落**：PR #90 の調査で意味構造を理由に拒否された135段落のうち、119段落が提案可能になった（同じ段落として100、表のセルや箇条書きの項目に正しく分かれて19）。残る15段落は、配置物が動く8件、リンクの文字3件、中央揃え2件など、安全のため拒否したもので、1件は調査の対象外だった。原因は1つではなく、7つの構造に分かれていた（1章）。
- **同じ母集団全体**：main で提案できたのは1,054段落中727段落、今回は883段落。新しく調べたタグ付きPDFでは196段落中12段落から183段落になった。main で提案できて今回できなくなった段落は0件。
- **保存までの結果**：固定した17件の要求では、7件が固定どおり保存できた。7件とも安全性の監査に合格し、構造ツリーは編集した ActualText 以外一致し、保存したPDFだけから条件付きで再編集できた（構造の検査の1項目は L-short で不合格。固定した期待文字列の誤りによる）。代替フォントを承認した経路では、さらに5件が保存できた。新たに提案可能になった段落から選んだ52件の実際の変更（短文化と長文化）では、31件を保存した。安全性の合格は24件、品質の合格は20件、構造の合格は31件。安全性の不合格7件では、どれも他の描画は消えも動きもしていない。5件は編集した段落自身の文字が元の段落の箱の外（承認した編集枠の中）に出たもの、2件は行末の全角空白（インクなし）の箱が承認枠の右端を越えたもの。
- **構造の扱い**：構造ツリーは書き換えない。変えるのは、編集した要素の `/ActualText` だけ。保存の前に、構造ツリーの正規形が元のPDFと一致することを証明する（2章）。MCID・ParentTree・IDTree・RoleMap・`/Lang` などは、すべての保存で変わらなかった。
- **既存の機能**：PR #87〜#90 の評価の結果は、PR #90 が記録した main の状態と一致した。PR #90 の74件の保存では1件だけ違い、main で容量のため拒否していた見出しが保存されるが、作者の改行を変える（4章）。
- **アーキテクチャ**：既存の方式（描画の書き換え）は本質的な障壁ではなかった。構造の判定を `semantics.py` に分け、描画の書き換えはその判定に従うだけにした。残る障壁（5章）は、埋め込みフォントにない文字、編集枠の幅の根拠、中央揃え、配置物の移動、作者の改行の保持である。いずれも構造ではなく、組版と描画の課題。

## 1. 拒否原因の分類

PR #90 の全段落調査で、意味構造を理由に拒否された段落は135件だった。拒否理由の文言だけでなく、段落を描くマーク付きコンテンツと構造ツリーの実際の形を、段落ごとに記録して分類した（`prototypes/paragraph_frame/tagged_diagnose.py`）。135件は1つの原因ではなく、次の7つの構造に分かれた。

| 件数 | 文書（生成元） | PR #90 の拒否理由 | 実際の構造 |
|---|---|---|---|
| 44 | issue14297（InDesignで配置したPDF） | mixed or nested marked-content scope | 構造ツリー（StructTreeRoot）がないのに、`/Figure <</MCID n>>` が残っている。その内側に `/PlacedPDF`。MCIDは意味を持たない |
| 27 | 府政だより477号（InDesign） | paragraph crosses a marked-content container | 段落の行の中に、配置されたアイコン（「問」など）が `/PlacedPDF` として描かれている。アイコンは自分のクリップとパスを持つ |
| 22 | 160F-2019（Acrobat Distiller 5） | unbound marked content | 表のセル `/TD` がMCIDを直接持つ。構造要素に `/Type` がないため、MCIDとの対応が認識されなかった |
| 15 | 府政だより477号 | replacement-text marked content requires a span adapter | 段落の中の空白1文字が、`/Span <</ActualText <U+0007>>> BDC` で囲まれている（InDesignの「先頭文字スタイルの終了」などの特殊文字） |
| 13 | 160F-2019 | mixed or nested marked-content scope | 1つのセルのMCIDが、見た目では2つ以上の段落を描いている |
| 11 | 160F-2019 | unbound marked content | 同じ行に並んだ複数のセルの文字が、1つの段落として推定されていた |
| 3 | word_osaka_guideline（Word） | multiple semantic paragraph parents | 複数の `/P` 要素の行が、1つの段落として推定されていた |

単純な P/Span 構造（Wordの `/P` と `/Span` 葉要素、ActualText と Lang 付き）は PR #88 で対応済みで、この135件には含まれない。

新たに見つけたタグ付きPDF（pdf.js のテストPDF）でも同じ調査をした。

| 文書（生成元） | 構造 | main の拒否理由 |
|---|---|---|
| prefilled_f1040（Adobe LiveCycle Designer） | `/P` が `/Div` の下にある。構造ツリーに `/IDTree` がある | 2ページ159段落のうち121段落が「IDTree references require richer semantic adapter」、37段落が「mixed or nested marked-content scope」 |
| issue16500（PDFTron）、zero_descent（iText） | `/P` が `/TD` の下にある | 一部は編集可 |
| issue11656（Word） | `/TagSuspect` の入れ子 | 拒否 |
| issue6782（Aspose.Words） | `/Part` の下の `/P` | 拒否（unsupported paragraph child） |

7つの構造それぞれに、何を根拠に何を許すかを決めた（2章）。

| 構造 | 扱い |
|---|---|
| 構造ツリーのないMCID（issue14297） | 意味を持たないので容器として残し、その内側に新しい文字を描く（2.1） |
| 段落の中のインライン配置物（府政だより） | 固定のシーケンスとして演算子を変えず、位置と内容の順序を保つ。再組版で動く場合は拒否（2.1、2.5） |
| `/Type` のない `/TD` のMCID（160F） | ISO 32000 で `/Type` は省略可能。`/S` があれば構造要素として扱い、`/TD` をブロック要素に含める（2.2） |
| 置き換え文字列の1文字（府政だより、U+0007） | 原子のシーケンスとして、元のグリフをそのまま囲む場合だけ残す（2.1） |
| 1つのMCIDが複数の段落を描く（160F） | 容器として残し、要素の内容項目を変えない（2.1） |
| 同じ行の複数のセル（160F） | 構造要素ごとに行を分ける（`split_blocks`） |
| 複数の `/P` の行（Word） | 構造要素ごとに段落を分ける。残った3件はリンク（`/Link` の下の `/Span`）で、安全のため拒否 |

## 2. 設計：描画の書き換えと構造の更新の分離

`prototypes/paragraph_frame/semantics.py` が、段落を描くマーク付きコンテンツと構造ツリーについて、元のPDFだけから次を決める。描画の書き換え（`auto_writer.py`）は、この決定に従ってストリームを組み立てるだけで、構造ツリーそのものは書き換えない（変えるのは編集した要素の `/ActualText` だけ）。

### 2.1 マーク付きコンテンツの扱い

段落の文字を描く各シーケンス（BDC/BMC … EMC）を、次のいずれかに分類する。どれにも当てはまらないものは拒否する。

| 分類 | 条件 | 扱い |
|---|---|---|
| 容器（container） | 段落の全体を囲み、段落以外も描く。MCIDのないもの（`/PlacedPDF`、レイヤー、アーティファクト）、構造ツリーのない文書のMCID、段落以外も描くMCID（表のセル） | BDC/EMC をそのまま残し、新しい文字をその内側に挿入する。構造要素の内容は変わらない |
| 再出力（mcid） | 段落の内側にあるMCID | 古い文字と一緒に BDC/EMC を外し、新しい文字の周りに同じ BDC を書き直す。編集で文字がなくなったMCIDも、空のシーケンスとして元の順序の位置に残す（構造要素の内容項目を失わない） |
| 再出力（plain） | 段落の内側にある、意味を持たないシーケンス | 同上 |
| 原子（atom） | 段落の内側にある `/ActualText`・`/Alt`・`/E` 付きのシーケンス（置き換え文字列） | 元のグリフをそのまま囲む場合だけ書き直す。編集でグリフがすべて消えれば一緒に消える。一部だけを変える編集は拒否する |
| 固定（fixed） | 段落の内側にある、文字以外も描くシーケンス（クリップ・パス・画像を持つインライン配置物） | 演算子を一切変えない。再組版後も元の位置にあることを確かめ（ずれる場合は拒否）、内容の順序も「前の文字 → 配置物 → 後の文字」に保つ |

拒否するもの：段落の境界をまたぐシーケンス、再出力するシーケンスの入れ子、Form XObject 内のMCID、置き換え文字列を持つシーケンスが段落を囲む場合。

### 2.2 構造ツリーの条件

再出力するMCIDは、次を満たす場合だけ扱う。

- MCIDを持つ要素は、ブロック要素（`P`、`H`、`H1`〜`H6`、`TD`、`TH`、`LBody`、`Lbl`、`Caption`、`BlockQuote`、`Note`、`Title`、`TOCI`、`Div`、`Sect`、`Art`、`Part`、`Document`、`Index`）か、ブロック要素の下のインライン要素（`Span`、`Quote`、`Code`、`Em`、`Strong`、`Sub`）。RoleMap をたどって判定する。
- 段落のMCIDは、1つのブロック要素の内容（直接のMCIDと、インライン葉要素のMCID）と、順序も含めて完全に一致する。段落の文字と要素の文字が同じものであることを保証するため。
- 要素が持つ項目は `/Type /S /P /K /Pg /Lang /A /C /T /ID /R /ActualText` だけ。`/Alt`・`/E`（代替説明・略語の展開）は、文字を変えると内容と食い違うため拒否する。
- 段落の中にリンク（`/OBJR`）がある場合と、別のストリームを指すMCR（`/Stm`）は拒否する。
- ブロック要素を囲む要素（表、セクションなど）が `/ActualText`・`/Alt`・`/E` を持つ場合は拒否する。囲む要素の置き換え文字列も編集した文字を含むため、古いまま残ってしまう。
- `/IDTree` は拒否しない。B2は構造要素を作ることも消すこともなく、`/ID` も変えないため、IDTree はそのまま正しい。
- `/ActualText` は、元の値が描かれた文字と一致する場合だけ扱い、編集後の文字に書き換える（葉要素ごと、およびブロック要素自身）。
- `/Lang` などの属性は変えない。

### 2.3 文字の対応づけ

複数のシーケンスにまたがる段落では、編集前後の文字列を1文字ずつ対応づける（difflib、autojunkなし）。変わらない文字は元のシーケンス（Span）に残り、変わった部分は、置き換えられた文字のシーケンスに入る（挿入なら直前の文字のシーケンス）。新しい文字が原子や固定のシーケンスに入ることはない。シーケンスが1つ以下の段落では、従来どおり前後の共通部分だけを残す（既存の結果を変えないため）。

### 2.4 公開前の証明

保存の前に、次を確かめる。1つでも満たさなければ公開しない。

- 構造ツリーの正規形（要素をルートからの位置で、ページを番号で、注釈をページと位置で表す）を、元のPDFと保存後のPDFで比べる。違ってよいのは、書き換えた要素の `/ActualText` だけ。ParentTree、IDTree、RoleMap、ClassMap、要素の子と順序、`/Lang` などはすべて同じでなければならない。
- 元のPDFで成り立っていた意味構造の検査（MCIDが構造ツリーに結び付く、MCIDが重複しない、ActualText が描かれた文字と一致する、ParentTree の逆方向の対応）は、保存後も成り立つ。元のPDFの別の場所にある既存の不整合は、編集を止める理由にしない（従来は、ページのどこかに不整合があると、すべての編集を拒否していた）。

### 2.5 実PDFの調査で必要になった、構造以外の共通処理

構造の扱いを直しただけでは、実PDFの多くはまだ保存できなかった。原因は構造ではなく、タグ付きPDFを作る製品に共通する描画の書き方だった。どれも特定のPDFやオブジェクト番号に頼らない共通処理として実装した。

| 現象（見つけたPDF） | 処理 |
|---|---|
| MediaBox の原点が (0,0) でない（160F: 原点が約12pt ずれ、文字が12pt ずれて描かれた） | ページ座標から既定ユーザー空間への変換をページ行列（`page.transformation_matrix`）の逆行列で行う。回転したページは拒否 |
| テキストが自分専用のクリップの中に描かれる（Distiller: `BDC Q q re W n BT …`） | 挿入位置の候補を、再出力するシーケンスの内側まで広げる。編集枠は、編集する文字自身のクリップとの共通部分に限る（配置物のグリフは除く） |
| 透明度やブレンドを設定したグラフィックス状態が、戻されないまま後続の描画に効いている（issue14297: GS2） | 挿入候補を順に試し、状態が無害な最初の位置に入れる。どこにもなければ、元の文字自身が不透明・通常ブレンドで描かれていた場合に限り、中立の ExtGState（`/PFNeutral`）を設定してから描く。元の文字にブレンドや透明度があれば拒否（`content_stream.State.blend` で実効状態を追跡） |
| 不透明な文字が `/AIS true`（アルファを形状として扱う）とオーバープリントの状態で描かれている（府政だより） | アルファが1でソフトマスクがなければ `/AIS` は描画に影響しないので拒否しない。新しい描画は元の文字と同じ `/OP`・`/op`・`/OPM` で描く。挿入位置で引き継ぐ状態が違えば、中立の ExtGState に元の文字のオーバープリントを入れて設定する（配置物の後ろの文字も同じ）。1つの段落で文字ごとにオーバープリントが違う場合（黒の文字はオーバープリント、色の付いた ■ はなし）は、設定ごとに中立の ExtGState を用意し、グリフの間で切り替えて、各グリフの元の設定を保つ |
| 行の先頭や末尾の記号が、本文から1pt前後ずれたベースラインに描かれ、ページの最後にまとめて塗られる（f1040 の ▶、府政だよりの ●） | 同じ構造要素の行で、ベースラインの差が小さい（0.05pt超〜小さい方の文字サイズの0.35em）、横に接している行を1行にまとめる。各グリフは元のずれを保つ。新しい描画は読み順に書くので、抽出順も読み順になる |
| 同じ記号で始まる箇条書きの各項目が、1つの段落と推定される（府政だより） | 段落の最初の行と同じ記号（Unicode の記号類、・※ など）で、同じ x から始まる行を次の項目とする |
| 1つの構造要素の中で、別のサイズの行が離れた位置にある（160F: 中央揃えの表題の下の注番号） | 同じ構造要素でも、サイズが違い、続きの行の x から始まらない行は別の段落とする |
| 中央揃えの段落（160F の表題） | 続きの行が1行目と同じ中心にあり、2em以上内側から始まる段落は拒否する（再組版すると行頭揃えになるため） |
| インライン配置物のクリップが、その BMC の前で設定され、EMC の後の Q まで続く（府政だより「問」アイコン） | 配置物の後ろの文字は、EMC の後で、クリップが編集枠を含む最初の位置に入れる。元の後続の文字より後ろには入れず、間に他の文字がないことを確かめる |
| 保存した記録が、再openで「古い」と判定される | 推定と記録で同じ行の作り方（`auto_detect.page_rows`）を使う。配置物のグリフも段落の行に含める。承認時に既に承認幅の中にあった保護対象の描画（フォーム欄、アイコンの塗り）を記録に残し、それ以外の描画が入った場合だけ古いと判定する |
| 2行の段落で1行目の方が長いと、後続段落の右端まで両端揃えで引き伸ばされた（issue14297: 表の見出しの下の行） | 両端揃えと判定するのは、最終行以外の行が編集枠の右端（承認値、または段落と後続段落の最も長い行）に届いている場合だけにする（PR #87 からの規則の修正） |
| 複数行の段落が、左隣の表見出しの左端を借りて、続きの行を元より左に置いた（issue14297） | 近くの行から左端を借りるのは、コメントの意図どおり1行の段落だけにする。複数行の段落は自分の続きの行の左端を使う（PR #87 からの規則の修正） |
| cmap のない TrueType フォント（160F） | 文字の対応の手がかりがないものとして扱う（例外で止まらない） |

## 5. 次に解消すべき技術的障壁

評価で残った拒否と品質不合格を、原因別に整理する。どれも、条件を緩めて通すのではなく、新しい根拠を得る処理が必要なもの。

1. **埋め込みサブセットにない文字。** 固定した要求17件のうち多くは、新しい文字が元の埋め込みフォント（サブセット）にないため、代替フォントの明示的な承認なしには保存できない。文字の追加は、元フォントのプログラムを取得できる場合のフォント拡張（同じ書体の不足グリフの追加）か、代替フォントの承認UIの整備が必要。今回は承認済み代替フォントの別経路として評価した（固定結果の置き換えではない）。
2. **編集枠の幅の根拠。** 1行の段落と、表のセルの中の段落は、元の描画の右端までしか広げられない（PDFは作者のテキスト枠を保存しないため）。セルの罫線、表の列の構造（`/Table` の構造と描画された線の対応）、段組の格子から右端を証明できれば、長文化の容量が増える。
3. **中央揃え・右揃え。** 中央揃えの段落は拒否している。行ごとの中心（または右端）を保つ配置を組版エンジンに加え、元の行の位置から揃えを証明できる場合に使う。
4. **Form XObject の中のMCID。** 今回の135件には含まれなかったが、Form の中の構造付きコンテンツは拒否を維持している。Form のコピーオンライトとMCIDの対応（ParentTree の `/StructParents` を持つ Form）を合わせて扱う必要がある。
5. **リンク（`/OBJR`）・代替説明（`/Alt`・`/E`）・複数シーケンスにまたがる `/ActualText`。** 安全のため拒否している。リンク注釈の矩形を新しい文字位置に合わせて動かす処理と、代替説明を利用者が確認する手順が要る。
6. **Poppler のページ全体の抽出順。** 行の折り返しが変わると、段組やフォーム欄が並ぶページでは、Poppler の全文抽出の順序が元と変わることがある（編集した領域の中の抽出は一致）。最小の編集（演算子の中の1文字の置き換え）でも同じ現象を確認しており、レイアウト解析の性質による。全文の一致を品質合格の条件として残し、領域内の一致は別の項目として報告している。また、新しい描画は元の文字より前の位置に挿入することがあり、描画順で抽出する場合（MuPDF の既定）に、隣の別の段落（ラベル）との順序が入れ替わる例が1件あった（3.3）。挿入位置を元の文字の描画順の位置に近づける処理が要る。
7. **構造要素の中の段落の境界。** 同じ構造要素の中の行は、サイズと開始位置が続きの行と合う限り1段落とし、縦の間隔は見ていない。1つのセルに離れた段落が2つあり、MCIDが共有されている場合などに、構造と描画の両方から境界を決める規則が要る。
8. **作者の改行を保つ。** 編集枠の右端は、段落と後続段落のうち最も長い行から推定する。見出しのように作者が途中で改行した段落では、変えていない行まで本文の幅で組み直してしまう（府政だより7ページの見出し、4章）。変えていない行の改行位置を保ち、変更を含む行から後だけを組み直す処理が要る。
9. **右から左の文字。** ヘブライ語やアラビア語の段落は、双方向の並べ替えと行分割がないため拒否している（issue11656）。
10. **インライン配置物を文字と一緒に動かす。** 135件で残った拒否の最多（8件）。今は配置物の演算子を一切変えないため、再組版で配置物の位置が変わる編集は拒否している。配置物のシーケンス全体を、行の移動量だけ `cm` で平行移動して描き直し、配置物の中のクリップ・画像・文字が変わらないことを監査で確かめる処理が要る。

# 編集の方式の比較（一回限りのPoC）と今後の推奨

2026-11-03。Issue #122。PR #121 マージ後の main `317905d` を起点とする。PoC と評価器は `experiments/route_poc/` にあり、main のエンジン・基準・製品契約は変えていない。比較の表は [comparison.json](../experiments/route_poc/comparison.json)、固定したケースは [cases.json](../experiments/route_poc/cases.json)。

## 結論

- **推奨は A（現方式を継続）**。根拠は16件の実測。
- 別の方式（PDFライブラリで段落を組み直す）の PoC は、現方式を上回らなかった。

| 16件（実PDF） | 保存 | 実用 | 再編集 | 復元 | 拒否 | 未検証 |
|---|---|---|---|---|---|---|
| 現方式（B2、候補をすべて承認） | 12 | **6** | 11 | 9 | 4 | 0 |
| PoC（ライブラリで組み直す） | 4 | **0** | 3 | 0 | 12 | 0 |

- **PoC で実測した改善**
  - 元の文書の字形の隙間で、現方式の検索・抽出が不合格になる L8・S-L1 で、PoC の検索・抽出は合格した。
    - ただし理由は、段落のすべての字形を代替フォントで描き直したこと。見た目が変わるので、2件とも実用ではない。
  - 実装が小さい：組み直しは299行。現方式は `prototypes/paragraph_frame` に65ファイル・18,430行（評価器を含む）。
  - 1手が速い：0.01〜0.65秒。
- **改善しなかったこと**
  - 利用者の操作数は減らなかった。保存した1手目で、PoC は3〜5、現方式は3〜6。
  - PoC は、現方式が個別に解いてきた次の問題を一つも解けず、拒否か不合格になった。
    - 実用の不合格：フォント、タグ、承認外の保護。
    - 拒否：後続の内容の移動、パネル・クリップ、段落の幅と改行の推定。
- **3択の根拠**
  - B（転換・併用）は採らない。代替の経路は実用0件で、唯一の利点（検索の正規化）は、全字形を代替フォントで描き直すことと切り離せない。
  - C（休止）は採らない。現方式は保存12・実用6を出しており、改善も実測で続いている（#120 で保存＋3）。
- **次の一手**（提案のみ。機能の Issue には自動で戻らない）
  - 現方式で、保存できたのに実用でない6件は、すべて検索・抽出の不合格だった（元の文書の隙間・抽出順）。
  - これを次の対象にするかは、利用者が判断する（7章）。

## 1. 比べた方式と選んだ理由

| 方式 | 内容 | この PoC での扱い |
|---|---|---|
| 現方式 B2（`prototypes/paragraph_frame`） | 内容ストリームの演算子を局所的に書き換える。段落の枠をサイドカーに記録する。後続の行・装飾・パネル・クリップは、ID を示して編集ごとに承認する。承認変更監査（`approved_audit`）と実用の判定（`eval_records.practical`）がある | 最善の経路（提案の候補をすべて承認）を、コミット済みの評価の結果から取った。再実行はしていない |
| 現リポジトリの `pdfeditor` の CLI | `compose-selected`、`edit-paragraph`、`propose-page`／`accept-page`／`replace-text` | 16件では実行していない（理由は下記）。比較の数には入れない |
| **案A：ライブラリで段落を組み直す**（今回の PoC） | クリックした段落を MuPDF の配置から読む。選択を置換し、元の字形を redaction（文字だけを除く）で消す。段落のフォントで組み直して書く | 実装して16件で実測した |
| 案B：ページを作り直す（別の形式に変換して PDF を再生成） | ページの字形・描画をすべて作り直す | 実装しない。承認外の保護（編集しない内容の字形・描画を変えない）を、構造上満たせないため。期待であり実測ではない |
| 案C：外部の製品（Acrobat など） | — | この環境にないので測っていない |

`pdfeditor` の経路は、クリック・選択・入力の3操作の外に、次を手で渡す必要がある。

- `compose-selected`：選択の JSON（`--selection`）と置換に使うフォントファイル（`--font`、必須）。
  - 元の書体・subset のコードを保たない、と CLI 自身が述べている。
  - 幅・高さ（`--width`、`--max-height`）は、確定した値を渡す。
- `edit-paragraph`
  - 事前に `inspect-paragraph` で作る段落の JSON（`--paragraph`）が要る。
  - 編集とフォントの対応の JSON（`--edits`）を渡す。
  - 幅・左端・下端（`--width`、`--x`、`--max-bottom`）は、確定した値を渡す。
- `propose-page` → `accept-page` → `replace-text`
  - 候補のフォントのディレクトリまたはファイルを渡す。
  - 段落 ID・提供フォントの選択（`--provider`、`--substitute-provider`）を渡す。
  - 状態ファイルを手で受け渡す。

これらの値を評価器が代わりに決めると、比較したい「利用者の操作から編集まで」の部分を手で補うことになる。そのため実行せず、未実行として記録する。

## 3. PoC（`experiments/route_poc/retypeset.py`）

利用者の操作は、クリック・選択・入力だけを渡す（`--at`、`--old`、`--new`）。演算子・字形 ID・枠・フォントファイル・候補 ID は渡さない。

1. 段落：MuPDF の配置（rawdict）から、クリックを含む段落を読む。
   - 基線で行をまとめる。
   - 次の箇所で切る：文字の大きさが変わる所、行の間隔が1.6倍を超える所、右端より1.5 em 以上短く終わる行（改行）の後。
   - 論理テキスト：行をつなぐ。英単語の間は空白、日本語・ハイフンの後は空白なし。
2. 選択：空白の有無を問わずに探し、クリックした字形を含む出現を置換する。
3. 消去：段落の字形を、文字だけを除く redaction で消す（`PDF_REDACT_TEXT_REMOVE`、画像・線画は残す）。何も塗らない。
4. 組み直し：段落の左端・1行目の開始・幅・行送り（描かれたまま）で組む。
   - 改行：英文は空白、日本語は任意の文字で（行頭・行末の禁則あり）。
   - フォント：段落の埋め込みフォントが新しい文字の字形をすべて持てば、それを使う。なければ代替フォント（見た目の変化。承認が要る）。
   - 書き込み：TextWriter で書く。大きさと色は段落のもの。
5. 段落が伸びる場合：伸びる帯に何も描かれておらず、段落を囲む枠・パネルの中にとどまることを確かめ、承認を求める。それ以外は、何が当たるかを示して拒否する。他の内容は動かさない。

評価器（`evaluate.py`）は、各ケースで次の2手を行う。

- 1手目：編集。まず承認なしで実行し、次に PoC が求める承認（空きへの伸び、代替フォント）を与えて実行する。
- 2手目：保存したPDFだけから、新しい文字をクリックして元に戻す。

保存した各手で、次を確かめる。

- 保存：編集範囲の新しい文字が期待どおり。
- 承認外の保護：編集範囲（旧・新、各1 pt 外側）の外で、次が元のままか。
  - 字形（原点の位置で判定）・描画・画像・注釈・リンク・他のページ
  - 画素（MuPDF 72/150 dpi、Poppler 72 dpi）
- 構造：MCID を失わない。新しい文字がタグの外になる、タグ付きのページでないこと。
- 検索・コピー：`search_copy.measure` と `verified`（Issue #114・#116 と同じ判定）。
- 見た目：段落のフォントを保つ。代替フォントは承認しても保つとは数えない。戻す編集が1手目で埋め込んだ代替フォントを使う場合も同じ。
- 配置：計画した基線に、すべての行が描かれる。

実用は、すべてが合格のときだけとする。測っていない項目は null とし、成功に数えない。

- 操作数：3（クリック・選択・入力）に、承認1件につき1を足す。
- 現方式の操作数も、同じ数え方で、承認した候補 ID の数から出した。

評価器の測定不具合の修正（実行の途中で見つけ、比較の表は修正後の結果）：

- 字形の保護の判定：字形を箱の重なりで除外していたため、次の行の高い字形（S-I1 の「■」）の消失を見逃していた。原点の位置で判定するように直した。画素の比較は修正前から不合格を出していた。
- フォントの判定：2手目で、1手目が埋め込んだ代替フォントを「段落の埋め込みフォント」と数えていた。元の段落のフォント名と比べるように直した。
- タグの判定：MCID の減少だけを見ていたため、タグ付きのページで新しい文字がタグの外になることを見逃していた。不合格とするように直した。

### 4.1 PoC で改善したこと（実測）

- 検索・抽出：L8・S-L1 の2件で、`search_copy.verified` が合格した（現方式は元の文書の隙間で不合格）。
  - 理由：段落全体を1つの文字列として書き直すので、元の隙間が消える。
  - 2件とも代替フォントで描いており、実用ではない。
- 保存できた4件の画素：編集範囲の外の画素は、3件で3つの描画（MuPDF 72/150 dpi、Poppler 72 dpi）とも0。何も塗らず、画像・線画も変えていない（S-I1 は 4.2）。
- 規模と速さ
  - 組み直しは299行、評価器を含めて825行。1手は0.01〜0.65秒。
  - 現方式（`prototypes/paragraph_frame`）は65ファイル・18,430行（評価器を含む）、`pdfeditor` は61ファイル・20,874行。
  - 現方式の1手の時間は、コミット済みの結果からは比べられる形で取れなかった。未比較とする。

### 4.2 改善しなかったこと（実測）

- **フォント**
  - 保存した4件のうち3件（L8・S-L1・S-I1）は代替フォントになった。埋め込みフォントは subset で、新しい文字（「月上」「6」など）の字形を持たない。
  - 字形を持っていたのは、Word の MS-Gothic（S-W2）の1件だけ。
  - 戻す編集も代替フォントのまま。復元の画素の差（MuPDF 72 dpi）：L8 2,397、S-L1 13,239、S-I1 22,314。
  - 現方式は、元の字形を保ち、新しい字形だけを足すので、この問題がない。
- **承認外の保護**
  - S-I1 で、redaction が次の行の「■」を消した。この字形の箱は上の行に重なっていた。
  - 消えたことで、MuPDF 72/150 dpi で 43/225、Poppler 72 dpi で 26 の画素が変わった。
  - 字形の箱を単位に消す方式では、隣の行の字形を巻き込みうる。
- **タグ**
  - S-W2 はタグ付きのページ。新しい文字はタグの外に書かれ、段落のタグは中身が空になった。
  - 現方式はタグの中で書き換える。
- **読み順**
  - S-L1・S-I1 で、戻した後のページの文字は同じ集合（S-I1 は「■」が欠ける）だが、抽出の順が変わった。
  - 書き直した段落がページの内容の最後に足されるため。
- **後続の内容**
  - 9件が、伸びる先に文字・画像があって拒否された。
    - 文字：R02・R03・R04・R14・R22・S-A1・S-T1。
    - 画像：R07・R10。
  - 現方式は、承認した後続の行・装飾を動かして、このうち R02・R03・R04・R14・S-A1 を保存している。
- **パネル・クリップ**
  - L2・W1・W2c は、段落が囲みを出るので拒否された。
  - 現方式はパネル・クリップの拡張を承認して保存し、うち L2・W1 は実用。
- **段落の幅・改行の推定**
  - S-T1 は短くする編集なのに、14行が15行になった。pdfTeX の両端揃え・ハイフネーションを再現しないため。
  - S-W2 の戻す編集は、1行が3行になって拒否された。1手目の短い行の幅を、段落の幅と読んだため。
  - S-I1 の戻す編集は、代替フォントの字幅で改行の位置が元と変わった。
  - 現方式は、枠をサイドカーに記録して再編集に使う。

### 4.3 現方式に残る弱さ（実測、コミット済みの評価から）

- 保存できたのに実用でない6件（L8・W2c・R03・R04・R14・S-L1）は、すべて「検索・コピー」が不合格。
  - 理由：元の文書の字形の隙間、行頭の「•」、Poppler の抽出順。いずれも元の文書でも同じ。
- 拒否の4件（R07・R10・R22・S-T1）：PoC もすべて拒否した。
- 操作数：パネル・クリップ・連鎖の承認で、3〜6操作。PoC も承認が要るので、操作数は同じ程度（3〜5）。

### 4.4 判定を緩めた場合（実測値からの再集計）

代替フォントを承認済みの見た目の変更として許すと、PoC で1手目が実用になるのは L8・S-L1 の2件だけ。

- S-I1 は承認外の保護が不合格のまま。
- S-W2 はタグが不合格のまま。

この場合も、現方式の6件を下回る。

## 5. 3択の推奨と根拠

**推奨：A（現方式を継続）。**

- 実測：同じ16件で、現方式は保存12・実用6・再編集11・復元9。PoC は保存4・実用0・再編集3・復元0。判定を緩めても PoC は実用2（4.4）。
- 実測：PoC が拒否・不合格になった理由は、現方式がこれまでの Issue で一つずつ解いてきた問題と同じ。
  - 後続の移動、パネル・クリップ、タグ、元の字形の保持、枠の記録。
  - 転換すれば、それらを作り直すことになる。
- 実測：PoC の利点は、検索・抽出の正規化と小ささ。
  - 正規化は、段落の全字形を描き直すことで得ており、元のフォントが subset である限り代替フォントと切り離せない（4件中3件）。
  - 併用（B）として、現方式の中で全字形の描き直しを使うと、見た目の変化と引き換えになる。

B（転換・併用）を採らない理由：

- 実用になった代替の経路がない。
- 併用で取り込める実測の利点（L8・S-L1 の検索の合格）は、代替フォントでの描き直しを前提にしている。
- 「見た目を変えて検索を直す」ことを許すかは、成功基準の変更になる（判断事項）。

C（休止）を採らない理由：

- 現方式は実用の成功を出している（6/16）。改善も実測で続いている（#120 で保存＋3）。

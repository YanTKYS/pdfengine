# 編集の方式の比較（一回限りのPoC）：stateless redaction＋段落再描画の実測

2026-11-03。Issue #122。PR #121 マージ後の main `317905d` を起点とする。

- PoC と評価器は `experiments/route_poc/` にある。main のエンジン・基準・製品契約は変えていない。
- 比較の表は [comparison.json](../experiments/route_poc/comparison.json)、固定したケースは [cases.json](../experiments/route_poc/cases.json)。
- PR #123 のレビューを受けて、次の2点を直した。
  - PoC が承認外の破壊を含むPDFを保存しない（3章 6・7）。
  - 結論の射程を、今回試した方式に限った（結論・5章）。

## 結論

- **今回検証した「stateless redaction＋段落再描画」方式（以下、経路X）は不採用とする。**
  - 経路Xは、毎回、保存済みPDFから段落を読み直し、redaction で消して書き直す。
  - 同じ16件で、実用0件だった。
- **方式の転換の可否、開発の継続・休止（Issue の3択）の最終判断は、この PoC からは導けない。利用者に留保する。**
  - 経路Xは、編集モデルを保持しない素朴な再描画である。
  - [独立アーキテクチャ評価](architecture-independent-review.md)（§1・§8）が推奨する方式とは別物である。推奨方式は、論理段落モデルを中心に置き、編集領域を再構築し、局所的にタグを付け直す。
  - 今回の結果は、その方式を反証しない（1章）。
- 次の2つは分けて報告する。
  - 現方式（B2）で限定した用途を短期的に改善する道は、有力。
    - 実測：16件で保存12・実用6。#120 で保存＋3。
  - Acrobat 型の自由な編集に到達できる見込みは、**今回の実験からは未確定**。
    - どの方式についても、それを測る実験をしていない。

|---|---|---|---|---|---|---|
| 現方式 B2（候補をすべて承認。コミット済みの評価の転記） | 12 | **6** | 11 | 9 | 4（0） | 0 |
| 経路X（今回新たに実行。出力前の監査つき） | 2 | **0** | 2 | 0 | 14（1） | 0 |

- 16件には、現方式の固定済みの成功6件が含まれる（2章）。
  - 比べているのは、現方式の既存の評価の転記と、経路Xの今回の新規実行である。
- 経路Xの最初の実行（`e792cd8`、PR 作成時）は、保存4・再編集3・拒否12だった。

| 外部の SDK・製品（Apryse、Acrobat など） | — | この環境にないので測っていない |

`pdfeditor` の経路は、クリック・選択・入力の3操作の外に、次を手で渡す必要がある。

- `compose-selected`
  - 選択の JSON（`--selection`）と、置換に使うフォントファイル（`--font`、必須）。
    - 元の書体・subset のコードを保たない、と CLI 自身が述べている。
  - 幅・高さ（`--width`、`--max-height`）は、確定した値を渡す。
- `edit-paragraph`
  - 事前に `inspect-paragraph` で作る段落の JSON（`--paragraph`）が要る。
  - 編集とフォントの対応の JSON（`--edits`）を渡す。
  - 幅・左端・下端（`--width`、`--x`、`--max-bottom`）は、確定した値を渡す。
- `propose-page` → `accept-page` → `replace-text`
  - 候補のフォントのディレクトリまたはファイルを渡す。
  - 段落 ID・提供フォントの選択（`--provider`、`--substitute-provider`）を渡す。
  - 状態ファイルを手で受け渡す。

これらを評価器が代わりに決めると、比較したい「利用者の操作から編集まで」を手で補うことになる。そのため実行せず、未実行とした。

## 3. 経路X（`experiments/route_poc/retypeset.py`）

利用者の操作は、クリック・選択・入力だけを渡す（`--at`、`--old`、`--new`）。演算子・字形 ID・枠・フォントファイル・候補 ID は渡さない。

1. 段落：MuPDF の配置（rawdict）から、クリックを含む段落を読む。
   - 基線で行をまとめる。
   - 次の箇所で切る：文字の大きさが変わる所、行の間隔が1.6倍を超える所、右端より1.5 em 以上短く終わる行（改行）の後。
   - 論理テキスト：行をつなぐ。英単語の間は空白、日本語・ハイフンの後は空白なし。
2. 選択：空白の有無を問わずに探し、クリックした字形を含む出現を置換する。
3. 消去：段落の字形を、文字だけを除く redaction で消す（`PDF_REDACT_TEXT_REMOVE`、画像・線画は残す）。何も塗らない。
4. 組み直し：段落の左端・1行目の開始・幅・行送り（描かれたまま）で組む。
   - 改行：英文は空白、日本語は任意の文字で（行頭・行末の禁則あり）。
   - フォント：段落の埋め込みフォントが新しい文字の字形をすべて持てば、それを使う。なければ代替フォント（見た目の変化。承認が要る）。
   - TextWriter で書く。大きさと色は段落のもの。
5. 段落が伸びる場合
   - 伸びる帯に何も描かれておらず、段落を囲む枠・パネルの中にとどまることを確かめ、承認を求める。
   - それ以外は、何が当たるかを示して拒否する。他の内容は動かさない。
6. **タグ付きのページは、何も書かずに拒否する**（レビュー後に追加）。
   - 新しい行がタグの外に描かれ、段落のタグが空になる（構造の破壊）ため。
7. **監査を通ったものだけを公開する**（レビュー後に追加）。
   - 結果を、出力の隣の一時ファイルに保存し、元のPDFと比べる（`audit`）。
     - 段落のもの以外の字形が、すべて同じ原点に残る。
     - 新しい段落の範囲の外に、新しい字形がない。
     - 描画・画像・注釈・リンクが同じ。
     - 他のページの内容が同じ。
     - 編集範囲の外の画素差が0（MuPDF 72 dpi）。
   - 合格なら、1回の rename で出力にする。
   - 不合格なら、一時ファイルを消し、出力は書かない（既存の出力にも触れない）。
     - 結果は `outcome='refused'`、`unsafe=True`。
     - 監査の結果（失った字形・画素差）を、診断として返す。

評価器（`evaluate.py`）は、各ケースで次の2手を行う。

- 1手目：編集。まず承認なしで実行し、次に経路Xが求める承認（空きへの伸び、代替フォント）を与えて実行する。
- 2手目：保存したPDFだけから、新しい文字をクリックして元に戻す。

保存した各手を、経路Xの監査とは別に、次の項目で測る。

- 保存：編集範囲の新しい文字が期待どおり。
- 承認外の保護：編集範囲（旧・新、各1 pt 外側）の外で、次が元のままか。
  - 字形（原点の位置で判定）・描画・画像・注釈・リンク・他のページ
  - 画素（MuPDF 72/150 dpi、Poppler 72 dpi）
- 構造：MCID を失わない。新しい文字がタグの外になる、タグ付きのページでないこと。
- 検索・コピー：`search_copy.measure` と `verified`（Issue #114・#116 と同じ判定）。
- 見た目：段落のフォントを保つ。
  - 代替フォントは、承認しても保つとは数えない。
  - 戻す編集が、1手目で埋め込んだ代替フォントを使う場合も同じ。
- 配置：計画した基線に、すべての行が描かれる。

実用は、すべてが合格のときだけとする。測っていない項目は null とし、成功に数えない。

- 操作数：3（クリック・選択・入力）に、承認1件につき1を足す。
- 現方式の操作数も、同じ数え方で、承認した候補 ID の数から出した。

測定と契約の変更の記録：

- **評価器の測定誤りの修正**（最初の実行の途中で見つけた。表は修正後の結果）
  - 字形の保護：字形を箱の重なりで除外していたため、次の行の高い字形（S-I1 の「■」）の消失を見逃していた。原点の位置で判定するように直した。画素の比較は、修正前から不合格を出していた。
  - フォント：2手目で、1手目が埋め込んだ代替フォントを「段落の埋め込みフォント」と数えていた。元の段落のフォント名と比べるように直した。
  - タグ：MCID の減少だけを見ていたため、タグ付きのページで新しい文字がタグの外になることを見逃していた。不合格とするように直した。
- **経路Xの契約の変更**（PR #123 のレビュー）
  - 最初の実行（`e792cd8`）では、経路Xは監査せずに保存しており、S-I1・S-W2 を `saved` として書き出していた。
  - 今は6・7のとおり拒否し、書かない。
  - 最初の実行の集計は `comparison.json` の `previous_poc_run` に残した。

### 4.1 経路Xで改善したこと（実測）

- 検索・抽出
  - L8・S-L1 の2件で、`search_copy.verified` が合格した。現方式は、元の文書の隙間で不合格。
  - 合格した理由：段落全体を1つの文字列として書き直したので、元の隙間が消えた。
  - 2件とも代替フォントで描いたので、実用ではない。
- 規模と速さ
  - 経路Xは374行（監査を含む）。評価器・比較・テストを含めると943行。1手は0.01〜0.85秒。
  - 現方式（`prototypes/paragraph_frame`）は65ファイル・18,430行（評価器を含む）。`pdfeditor` は61ファイル・20,874行。
  - 現方式の1手の時間は、コミット済みの結果から比べられる形で取れなかった。未比較とする。

### 4.2 改善しなかったこと（実測）

- **フォント**
  - 保存した2件はどちらも代替フォントになった。埋め込みフォントが subset で、新しい文字（「月上」など）の字形を持たない。
    - 最初の実行では S-I1 も同じだった。字形を持っていたのは、Word の MS-Gothic（S-W2）だけ。
  - 戻す編集も代替フォントのままで、復元は0件。
    - 復元の画素差（MuPDF 72 dpi）：L8 2,397、S-L1 13,239。
  - 現方式は、元の字形を保ち、新しい字形だけを足すので、この問題がない。
- **承認外の保護**（最初の実行で、破壊を含んだまま保存していた）
  - S-I1 で、redaction が次の行の「■」を消した。この字形の箱が、上の行に重なっていた。
    - 画素差：MuPDF 72/150 dpi で 43/225、Poppler 72 dpi で 26。
  - 字形の箱を単位に消す方式では、隣の行の字形を巻き込みうる。
  - 今は、監査がこれを見つけ、書かずに拒否する。
- **タグ**（最初の実行で、構造を壊したまま保存していた）
  - S-W2 はタグ付きのページ。新しい文字はタグの外に書かれ、段落のタグは中身が空になった。
  - 今は、書かずに拒否する。
  - 現方式は、タグの中で書き換える。
- **読み順**
  - S-L1 で、戻した後のページの文字は同じ集合だが、抽出の順が変わった。
  - 書き直した段落が、ページの内容の最後に足されるため。
- **後続の内容**
  - 9件が、伸びる先に文字・画像があって拒否された。
    - 文字：R02・R03・R04・R14・R22・S-A1・S-T1。
    - 画像：R07・R10。
  - 現方式は、承認した後続の行・装飾を動かして、このうち R02・R03・R04・R14・S-A1 を保存している。
- **パネル・クリップ**
  - L2・W1・W2c は、段落が囲みを出るので拒否された。
  - 現方式は、パネル・クリップの拡張を承認して保存し、うち L2・W1 は実用。
- **段落の幅・改行の推定**
  - S-T1 は短くする編集なのに、14行が15行になった。pdfTeX の両端揃え・ハイフネーションを再現しないため。
  - 最初の実行の S-W2 の戻す編集は、1行が3行になって拒否された。1手目の短い行の幅を、段落の幅と読んだため。
    - 経路Xは段落の枠を記録しない（stateless）。
  - 現方式は、枠をサイドカーに記録して再編集に使う。
- **操作数**
  - 保存した1手目で、経路Xは4〜5、現方式は3〜6。減らなかった。

### 4.3 現方式に残る弱さ（実測、コミット済みの評価から）

## 5. 3択について（判断は利用者に留保）

この実験で言えること（実測）：

- 経路X（stateless redaction＋段落再描画）は不採用。
  - 理由：同じ16件で実用0件。判定を緩めても2件。
  - 不合格・拒否の理由は、次のとおり。
    - 元の字形を保持しない（subset のため代替フォント）。
    - 段落の枠・関係を記録しない（stateless）。
    - 後続・パネル・クリップを動かさない。
    - タグを付け直さない。
    - redaction が隣の字形を巻き込む。
  - 経路Xの唯一の利点（検索の正規化）は、全字形を代替フォントで描き直すことと切り離せない。
- 現方式は、この選定集合で保存12・実用6を出している。限定した用途を短期的に改善する道としては有力。

この実験で言えないこと：

- 編集モデル中心の方式（独立評価 §8 の B）の優劣：経路Xは、その方式ではない。
  - §8 の方式は、論理段落モデルの保持、元の字形の provenance、局所的なタグの付け直しを含む。
  - 経路Xの失敗の多くは、まさにそれらを持たないことから来ている。
- 方式の転換（3択の B）・継続（A）・休止（C）のどれが正しいか。
  - 転換先の候補を実測していないので、A と B を比べられない。
  - 外部の要因（ライブラリ・SDK）も測っていないので、C の根拠もない。
- Acrobat 型の自由な編集に、どの方式で到達できるか：今回の実験からは未確定。

最初の版で書いた「推奨 A」「B は採らない」「C は採らない」は、この PoC の劣位からは導けなかった。撤回する。
